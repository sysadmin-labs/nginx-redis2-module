# Changelog

Newest first.  Dates are release dates.

## v0.16 (2026-10-13)

### Fixed

- `redis2_pass` with a variable in it built its upstream out of an
  `ngx_url_t` that nothing had zeroed: three of its fields were filled in
  and the rest was whatever the stack held.  Nothing in the versions this
  builds against reads one of the unset fields -- `default_port` was read
  there on nginx older than 1.11.6, which is long out of the matrix -- so
  what this fixes is latent rather than a failure anyone can produce
  today.  Every other `ngx_url_t` in nginx reaches its reader memzero'ed
  first, and this one does now too.

### Added

- A `LICENSE` file.  The grant was in the README, at line 745 of it, and
  nowhere else: not in a licence file, not in a single source header.  The
  wording is lifted verbatim.

- A test suite that needs nothing but nginx and this module.  The one that
  came with the module needs `echo`, `eval`, `set-misc`, `ngx_devel_kit`,
  `lua-nginx-module` and a LuaJIT to go with it -- six foreign modules to
  ask one module a question.  Every block here starts with `select 13` and
  `flushdb`, so the reply is fully determined and the suite can neither be
  disturbed by, nor disturb, anything else in that server.

- `t/reply.t`, which is the one that matters.  The parser's job is to find
  the end of a reply in a stream that arrives in pieces nobody chose, so
  these blocks make the pieces small (`redis2_buffer_size 64`) and the
  replies large, up to a megabyte.  The values are made with `setrange`
  rather than written out: it pads with NUL, so one short directive produces
  a reply of any length, and the NUL bytes also show that nothing in the
  path treats a value as a C string.

- `ci/hostile.sh` and a workflow of its own.  A real Redis server is well
  behaved -- it writes a whole reply in one go -- so the cases the parser
  exists for have to come from somewhere else: a pretend server that sends a
  bulk reply one byte at a time, one that cuts the length header into `$10`,
  `00\r` and `\n`, one that promises 100000 bytes and sends three, one whose
  first byte is not a reply type at all, one that sends a second reply nobody
  asked for, and one that accepts the request and says nothing.  It uses no
  Redis at all.

- `ci/redis.sh`, one script that starts a Redis for the suite and leaves an
  already running one alone, used by every workflow that needs one.  A
  service container would have been the other way, but then the image tag
  would live in each workflow: a job's `services` start before any step of
  that job runs, so nothing can read `.github/versions.env` first.

- `ci/parser.sh` and the `parser` workflow.  `src/ngx_http_redis2_reply.c`
  is generated by ragel from the `.rl` files beside it and is checked in, so
  a build needs no ragel -- and that is exactly how a fix lands in the
  generated file instead of in its source, works, ships, and disappears the
  next time anyone regenerates.  The workflow regenerates and asks git
  whether anything moved.  ragel is pinned at 6.10 and built from source,
  because two ragel releases produce different output from the same input
  and the distribution's version moves with the runner image.

- The gate ignores one thing, measured rather than assumed: ragel writes
  `#line <n> file.c` markers that point into the file it is generating, and
  two builds of ragel 6.10 number them differently.  The same input through
  the same release gave 18/288/308/615 here and 13/279/295/578 on the
  runner, with the rest of the file identical byte for byte and the gap
  growing with the amount of table emitted.  Those markers are bookkeeping
  about the output; a gate failing on them would be failing on the machine.
  Everything else is compared exactly, the markers pointing back into the
  `.rl` files included -- those do say which source produced what.

- The two constants ragel emits and nothing reads are now commented out
  instead of deleted.  Upstream deleted them, which left every `#line`
  marker after that point naming a line five further down than the one it
  sits on.  Same number of lines, same silenced warning, markers that are
  true again.

- The scaffolding the other modules in this organization carry: a version
  and digest pin for every build input in `.github/versions.env`, the
  release matrix, the FreeBSD virtual machine, A/UBSan, valgrind, CodeQL,
  shellcheck and actionlint, and eight reloads in a row with a probe that
  asks the module rather than the server.

### Changed

- `ci/build.sh` configures nginx with `--with-debug` and nothing else.  This
  module talks to Redis over a plain socket and the suite needs no other
  nginx module to ask it anything.

- A debug message said "done multi bunlk reading!".  Fixed in
  `src/multi_bulk_reply.rl` and in the generated file, which is the point of
  the `parser` gate: fixing only one of the two would have been invisible.

### Removed

- `util/build.sh`, the author's own build wrapper, which pointed at a home
  directory and at `ngx-build` from the openresty development utilities.
  What it did with ragel is now in `ci/parser.sh`.

- `util/fix-clang-warnings`, a Perl script that stripped two unused
  constants out of the generated parser so that clang's `-Werror` would
  accept it.  Same job, same reason, now four lines inside `ci/parser.sh`
  and keyed on the names rather than on line numbers.

- `misc/serv.erl`, an Erlang program that pretends to be a Redis server.
  `ci/hostile.sh` does that in Perl, which the suite already needs.

- The upstream `.github/workflows/ci.yml`, which cloned eleven repositories,
  built a LuaJIT and ran the suite under `no-pool-nginx`.
